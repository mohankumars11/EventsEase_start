# Admin Command Center — Phase 1 audit

Branch `feature/admin-partner-customer-lifecycle`, starting commit `21db2e2`.
Database inspected live with the service-role key against the real project.

Companion artifact: [`partner-onboarding-field-map.md`](./partner-onboarding-field-map.md),
generated by `scripts/build-onboarding-field-map.mjs`.

---

## 1. What already exists (and must not be rebuilt)

The brief's sections 4.1 and 4.3 ask for a partner master record and a trade +
field registry. **All three already exist**, so Phase 2 extends them rather than
inventing a parallel model.

| Asked for | Exists as | State |
|---|---|---|
| Central partner master | `vendors` (+ `partner_*` satellites) | in use |
| Trade registry | `sambramo_trade_registry` — 34 rows, all `active` | in use |
| Field registry | `sambramo_canonical_fields` | **booking fields only — 17 rows** |
| Per-trade field map | `sambramo_trade_field_map` — 375 rows | booking-time, not onboarding |
| Submission history | `sambramo_listing_versions` | present |

195 tables/views in total. The marketplace, escrow, dispatch, payout, referral and
story subsystems are all live and must be preserved.

## 2. The central finding

**Every onboarding answer for all 34 trades is stored in a JSONB blob.** There is
no typed column for any of them.

| Stage | Table | Column |
|---|---|---|
| In progress | `sambramo_listing_drafts` | `data` (jsonb) |
| Submitted | `vendor_services` | `specs` (jsonb) |

This is precisely what section 4.2 forbids as the sole storage mechanism, and it is
why the admin console cannot today filter partners by a trade-specific attribute —
"all caterers who serve over 500 guests" is not a query against `specs`, it is a
full scan and a client-side filter.

`sambramo_canonical_fields` looked like the typed registry the brief wants. It is
not: it holds 17 field ids and they are **booking-time** inputs (`guest_count`,
`duration_hours`, `route_distance_km`), used to price a job. None of the 249
onboarding questions has a typed definition anywhere in the database.

## 3. Where the real question definitions live

`src/data/trades/*.js` — 34 spec files in a small declarative language
(`src/data/trades/schema.js`). Each question carries an id, label, type,
required flag, bounds, option list and conditional visibility. This is the
authoritative description of the onboarding form, and it is machine-readable,
which is why the field map is **generated** from it rather than transcribed.

Scale, counted from the specs:

| | |
|---|---|
| Trades | 34 |
| Profile questions | **249** (152 required) |
| Catalogue sub-form fields | **241**, across 24 trades |
| Conditional questions | 11 |
| Form types in use | text, textarea, url, single, multi, number, money, toggle, date, time, dimensions, photos |

The **catalogue** fields are a repeating sub-form — a beverage menu, a vehicle
list, a set of rentable items. They are rows, not columns, so they belong in a
child table per trade, not flattened onto the profile.

## 4. Cross-check: specs vs database

`sambramo_trade_registry.required_answers` independently lists each trade's
required keys. Comparing it against the generated map:

**33 of 34 trades agree exactly.**

One drift:

| Trade | Finding |
|---|---|
| `transportation` | `other_description` is required in the spec but absent from `required_answers` in the database |

`anchor_mc` has zero spec questions by design — it predates the engine and runs
its own legacy flow (`legacyFlow`), so its data model is separate and must be
handled explicitly rather than assumed to match the other 33.

## 5. Consequences for Phase 2

Promoting 249 answers into typed columns implies roughly:

- **34 trade profile tables**, one per registry id, ~7 typed columns each
- **24 catalogue child tables**, for the repeating sub-forms
- a backfill out of `vendor_services.specs` with per-field mapping
- indexes on the fields the console will filter by

Two things make this riskier than the count suggests:

1. **Migrations here are applied by hand**, pasted into the Supabase SQL editor.
   ~58 new tables plus a backfill is a very large paste, and a partial apply
   leaves the schema inconsistent. It should be split into reviewable parts with
   a verification query after each.
2. **`specs` keys are not uniformly the spec's field keys.** Sampled rows contain
   namespaced keys (`emcee:hours`, `emcee:languages`, `anchor_v3`, `answers`)
   alongside plain ones. The backfill cannot assume `specs->>field_key` and must
   be driven by an explicit per-field mapping, with unmapped fields reported
   rather than dropped.

Only 15 of 400 sampled `vendor_services` rows carry non-empty `specs`, and
`sambramo_listing_drafts` holds 7 rows. So the backfill volume is small today —
which makes this the cheapest moment to do it.

## 6. Phase 2 finding: there is almost nothing to backfill

The schema generated cleanly (57 tables, migrations 173-178). The backfill, dry-run
against live data, did not.

Of 514 `vendor_services` rows, **22 carry any `specs` at all**. Matching their stored
keys against the current spec field keys:

| Trade | Rows | Stored keys | Matched a column | Columns available |
|---|---|---|---|---|
| anchor_mc | 5 | 79 | **0** | 0 (legacy flow, no spec file) |
| catering_food | 6 | 258 | 24 | 12 |
| photography | 2 | 41 | 5 | 9 |
| venue | 2 | 38 | 6 | 19 |
| bridal_makeup_hair | 3 | 25 | **0** | 6 |
| decoration_floral | 1 | 18 | **0** | 5 |
| cake_desserts | 1 | 16 | **0** | 12 |
| dj_music | 1 | 3 | **0** | 13 |
| mini_truck_pickup | 1 | 3 | **0** | 5 |

**35 of roughly 481 stored keys resolve to a typed column — about 7%.**

The reason is not a bad mapping. The stored answers come from an **older
questionnaire** than the one in `src/data/trades/`. Catering's blob carries
`catering:fssai`, `cooks:team`, `ops:trust:years`, `ops:serving:servers_per_100` —
a namespaced vocabulary that the current spec does not contain at all. 158 distinct
stored keys have no column anywhere.

So section 4.4's "backfill existing partner onboarding answers into their
corresponding trade-specific columns" has almost no work to do, and claiming a
successful migration would be claiming something false. What is true:

- The typed schema is correct for **new** submissions; the engine writes current
  field keys.
- Historical answers stay in `vendor_services.specs`, untouched, and the whole blob
  is also copied to `source_specs` on the profile row when one is created.
- The admin console must therefore read the typed columns **and** fall back to
  `specs` for legacy rows, or 22 partners appear blank.

Hand-mapping 158 legacy keys across a since-replaced questionnaire, to recover
answers for 22 listings, is not worth it. That is a recommendation, not a decision —
it is reversible at any time by extending the resolver in
`scripts/backfill-trade-profiles.mjs`.

as a regenerable artifact.

Phases 2–8 (schema, shell, partner workspaces, onboarding review, commercial
