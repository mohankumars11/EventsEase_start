# Migrations 154 and 155 — promotions and referral

Paste in order. Both are new tables; nothing existing is altered.


## Nothing appears until you configure a campaign

That is deliberate. With 154 applied and no rows, the Earnings tab looks
exactly as it does today — no card, no placeholder, no "coming soon".

**No rupee value exists anywhere in the app bundle.** A reward written
into a component cannot be changed without a release, is different on
every phone because partners update when they feel like it, and is a
commercial commitment made by whoever edited the file.

## To run the referral campaign you described

```sql
INSERT INTO public.partner_promotions
  (type, title, subtitle, body, cta_label, cta_route,
   reward_type, reward_paise, qualification, audience,
   terms_url, priority, active)
VALUES (
  'referral',
  'Grow the Sambramo community',
  'Refer & earn',
  'Know event professionals who should be on Sambramo? Invite them.',
  'Invite partners',
  '/dashboard/vendor?tab=account&screen=profile',
  'cash',
  250000,                                    -- ₹2,500, in PAISE
  '{"minimum_referrals": 20, "requires": "first_eligible_event"}'::jsonb,
  '{"lifecycle": ["LIVE"]}'::jsonb,          -- only live partners
  'https://sambramo.com/terms/referral',
  10,
  true);
```

`reward_paise` is **paise**. 250000 = ₹2,500. Every amount in this
database is paise and mixing the two is how somebody eventually gets
paid a hundredth of what they are owed.

## What a referral has to do before anybody is paid

```
invited → registered → onboarding_completed → verified → live
        → first_event_completed → reward_unlocked
```

Only the last two count toward the threshold. Everything before
`first_event_completed` can be manufactured by one person with a phone;
a completed event cannot — it needs a customer who chose them, money
through escrow, and a date that passed.

**Refused automatically:** referring yourself, being referred twice, the
same phone (compared on the last ten digits), the same identity document,
the same UPI id or bank account.

Every refusal returns the same sentence to the partner —
*"That code cannot be used on this account."* — while recording the real
reason in `rejected_reason` for you. Telling somebody which check caught
them tells them what to change next time.

## Paying a reward

`reward_unlocked` means *qualifies*, not *paid*. Nothing in the referral
system moves money. When you want to pay one:

```sql
SELECT public.record_adjustment(
  '<vendor uuid>', NULL, 'incentive', 250000,
  'Referral reward — 20 qualified referrals');
```

That is the existing operator-only path from migration 140, which writes
an auditable row with a reason on it. The referral row then points at the
adjustment via `adjustment_id`.

## Advancing the lifecycle

```sql
SELECT public.refresh_referral_states();
```

Operator-only, safe to run as often as you like. It recomputes every
referral's state from facts rather than incrementing counters — so a
path nobody wired up produces a stale number for one run, not a partner
permanently stuck one step short of a reward they earned.
