## Probes

### ① The self-verify hole is closed

Before anything else, see whether it was ever exploited. On a pre-launch
database this should be a short and explicable list:

```sql
SELECT id, business_name, is_verified, is_featured, created_at
  FROM vendors WHERE is_verified OR is_featured
 ORDER BY created_at DESC;
```

Then confirm the guard is on:

```sql
SELECT tgname FROM pg_trigger WHERE tgname = 'vendors_self_verify_guard';
```

### ② Geography works

```sql
SELECT ST_Distance(
  point_of(12.9352, 77.6245),   -- Koramangala
  point_of(12.9784, 77.6408)    -- Indiranagar
)::int AS metres;
```

**Expect roughly 5,000–5,200 m.** If you get a number in the millions,
latitude and longitude were swapped somewhere — but `point_of` rejects
out-of-range values precisely to make that impossible, so a wild number
means something else is wrong.

```sql
SELECT point_of(77.6245, 12.9352) IS NULL AS swap_rejected;  -- expect: true
```

### ③ Table and policies landed

Substitute the table name:

```sql
SELECT tablename, rowsecurity FROM pg_tables WHERE tablename = 'booking_lines';
SELECT policyname, cmd FROM pg_policies WHERE tablename = 'booking_lines';
```

`rowsecurity` must be `true`. A table with RLS off is readable by every
authenticated user.

### ④ The one-winner index exists

This is the constraint the whole dispatch model rests on:

```sql
SELECT indexdef FROM pg_indexes WHERE indexname = 'uq_offer_one_winner';
```

Must include `WHERE (status = 'ACCEPTED'::text)`. **A unique index
without that predicate would allow only one offer per line, ever** — it
would break dispatch entirely rather than protect it.

### ⑤ The race, on purpose

The important test. Two accepts on one line must produce one winner.

```sql
-- Two offers on the same line, both live.
INSERT INTO dispatch_offers (line_id, vendor_id, partner_amount_paise, expires_at)
VALUES ('<line-uuid>', '<vendor-a>', 1000000, now() + interval '5 min'),
       ('<line-uuid>', '<vendor-b>', 1000000, now() + interval '5 min');

-- Force both to ACCEPTED. The second must fail with 23505.
UPDATE dispatch_offers SET status='ACCEPTED' WHERE vendor_id='<vendor-a>' AND line_id='<line-uuid>';
UPDATE dispatch_offers SET status='ACCEPTED' WHERE vendor_id='<vendor-b>' AND line_id='<line-uuid>';
```

**The second UPDATE must raise `duplicate key value violates unique
constraint "uq_offer_one_winner"`.** If it succeeds, stop — two masters
can win one job, and everything downstream of that is wrong.

### ⑥ Escrow cannot go negative or be edited

```sql
-- A release with no hold behind it must be refused.
INSERT INTO escrow_ledger (line_id, kind, amount_paise, counterparty)
VALUES ('<line-uuid>', 'RELEASE_PARTNER', -1000, 'partner');
-- expect: escrow balance for line ... would go negative

-- And nothing is editable.
UPDATE escrow_ledger SET amount_paise = 1 WHERE id = '<any>';
-- expect: escrow_ledger is append-only
```

### ⑦ The collar is enforced by the database

The +8% cap is a promise made to a customer, so it is a CHECK, not a
JavaScript guard:

```sql
INSERT INTO quote_revisions
  (subject_type, subject_id, checkpoint, locked_paise, floating_paise,
   total_paise, baseline_floating_paise, pricing_version)
VALUES ('event', '<uuid>', 'revision', 100000, 120000, 220000, 100000, 'test');
-- expect: violates check constraint "quote_revisions_collar_holds"
--         (120000 is +20% on a 100000 baseline)
```

> **Keep in step:** the constraint hardcodes `108`. `COLLAR.cap` in
> `src/config/pricing.js` is `0.08`. If you change one, change the other —
> `scripts/check-dispatch-invariants.mjs` will assert this.

### ⑧ A partner still cannot self-verify, and history is logged

```sql
SELECT verification_status, is_verified, count(*)
  FROM vendors GROUP BY 1, 2;
```

Every row must satisfy `is_verified = (verification_status = 'approved')`
— the constraint enforces it, so a failure here means the backfill did
not run.

### ⑨ The masked feed leaks nothing

```sql
SELECT column_name FROM information_schema.columns
 WHERE table_name = 'partner_offer_feed';
```

**`address_text`, `customer_id`, `full_name` and `phone` must NOT appear.**
The view is built so a leak needs a schema change rather than a forgotten
filter.

And the scrubber:

```sql
SELECT scrub_contacts('call me on 98765 43210 or ravi@example.com before you come');
-- expect: call me on [removed] or [removed] before you come
```

# Follow-ups: 070 and 071

Two small files, found by running `scripts/check-dispatch-invariants.mjs`
against the applied schema. Both are re-runnable and touch no data.

## 070 · `point_of_india_bbox`

057's `point_of()` rejected impossible coordinates (±90 / ±180). It could
not reject a **swapped** one, and that is the mistake that actually
happens:

```
Bengaluru      12.9352 N, 77.6245 E
swapped        lat 77.6245  ← a valid latitude. It is in the Kara Sea.
```

The swapped point stores cleanly, indexes cleanly, and matches nothing
near Koramangala — a dispatch that finds no partners and reads as a
supply problem rather than a coordinate that went in backwards.

070 adds an India bounding box (lat 6–38, lng 67–98.5), so the swap now
fails on the longitude. Generous on purpose: the whole country, so Delhi
or Mumbai needs no migration.

It also adds **`set_vendor_location()`**, which the seeder needs —
PostgREST cannot write a `geography` column at all, so every coordinate
must go through a server-side function. That is a happy constraint: there
is now no path into `vendors.location` that skips the validation.

## 071 · `synthetic_vendors_have_no_login`

`vendors.profile_id` is `NOT NULL` → `profiles.id` → `auth.users.id`. So
seeding 200-plus test partners would create 200-plus **real auth
accounts** for businesses that do not exist — and somebody could sign in
as "Sri Lakshmi Decorators" and accept jobs from inside that session.

071 relaxes it to a conditional:

```sql
CHECK (is_synthetic OR profile_id IS NOT NULL)
```

A real partner still must have a login. A seeded one has none, and since
every partner RLS policy is `profile_id = auth.uid()`, a NULL makes them
unownable by construction — no policy rewritten.
