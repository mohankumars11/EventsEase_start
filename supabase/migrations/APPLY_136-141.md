# Applying 136–141 — partner earnings and payouts

Six files, pasted **in order**, into the Supabase SQL editor. Each is
`BEGIN; … COMMIT;` and re-runnable, so a file that fails leaves nothing
behind.

They are numbered 136–141 because 130–135 were taken by the calendar and
availability work in the same week. There is no dependency between the
two sets.

---

## Before you start

```sql
SELECT DISTINCT status FROM public.payout_claims;
```

Anything other than `requested`, `paid` or `rejected` will abort 137.
That is safe — the transaction rolls back — but it reads like a mystery
unless you have looked first.

After each paste:

```
node scripts/check-migration-columns.mjs
```

## 137 — paste the whole file in one go

`claim_payment` gains a second argument, and a new argument cannot be
added with `CREATE OR REPLACE`: two overloads both match a one-argument
call and PostgREST answers every claim with *function is not unique*. So
the file does `DROP FUNCTION` then `CREATE`.

Inside one transaction nobody sees the gap. **A file pasted half way
leaves production with no `claim_payment` at all**, and the DROP also
discards migration 091's `GRANT`, which is re-issued at the bottom.

## 139 — this is the one where money moves

Read its header before pasting it. Three things worth repeating:

- **Every `escrow_ledger` insert is permanent.** The table is append-only
  by trigger. A wrong settle can only be compensated, never undone.
- **A settled line writes four rows summing to zero** — `RELEASE_PARTNER`
  (the net, what actually reaches the bank), `REMIT_TCS`, `REMIT_TDS`
  (omitted when waived) and `RELEASE_PLATFORM`. This is why two CHECKs
  are widened: there was no ledger kind for a statutory remittance, and
  recording the *share* as released would have left the ledger unable to
  reconcile against a bank statement.
- **A short balance refuses rather than prorating.** If a refund or
  penalty has already run against the line, splitting what is left is a
  human judgement, not a number to invent into an append-only ledger.

The two tax rates are plpgsql constants. `src/config/legal.js` is the
source of truth and `scripts/check-payout-states.mjs` parses both and
fails if they drift.

### The first real settle

There is no operator console this round. Use the wrapper, not the SQL
editor:

```
node scripts/settle-claim.mjs --list
node scripts/settle-claim.mjs --claim <uuid> --ref <UTR>          # dry run
node scripts/settle-claim.mjs --claim <uuid> --ref <UTR> --confirm
```

The dry run prints the split — share, TCS, TDS, **what to transfer** —
and writes nothing. Transfer that amount, then confirm.

Run `node scripts/audit-partner-money.mjs` after the first one, before
doing a second.

## Why there is no `generated_documents` table

A payment slip is a pure function of rows the partner can already read.
Persisting one buys a storage bucket, a policy on it, a generator that
must run somewhere, a regeneration story for when a reference is
corrected, and a second source of truth that can disagree with the
screen — for a document that nothing is filed with and no counterparty
receives.

What was needed was stable identity, and that is derived:
`SB/PS/FY2526/<first 8 of the claim id>`, in
`src/lib/documents/slipModel.js`.

If immutability is ever required, the right object stores the **inputs
and a sha256**, not the bytes, and can be added later without touching
anything built here.

## What these migrations still do not give you

- **A payout provider.** Razorpay is customer-capture only. `adapter`
  has a `'RazorpayRoute'` value and nothing has ever written it.
  Transfers remain a person with a bank app.
- **Automatic payouts, a payout schedule, a minimum payout.** No
  preferences table and nothing that runs on a schedule. The UI does not
  render those toggles, deliberately.
- **An expected payout date.** Nothing can predict when a human runs a
  transfer. `partner_earnings.claimable_at` is what *is* derivable, and
  it matches `claimable()` exactly.
- **Tips or customer incentives.** No column anywhere. After 140 a
  manually granted bonus is a real adjustment row — but only once
  somebody has actually granted one.
- **GST tax invoices.** No GSTIN is stored, nothing is numbered
  continuously, and no place of supply is recorded. The document is a
  payment slip and says so on its face.

## Rollback

There is none for 139, by design — the ledger is append-only. 136, 137,
138, 140 and 141 are additive and can be dropped if nothing has written
to them yet:

```sql
DROP VIEW IF EXISTS public.partner_earnings;
DROP TABLE IF EXISTS public.partner_adjustments;
DROP TABLE IF EXISTS public.payout_batches CASCADE;
DROP TABLE IF EXISTS public.money_audit;
```

`partner_jobs` reverts by re-pasting migration 080.
