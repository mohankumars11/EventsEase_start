## 204 — security fix

Found by `check-event-spine-live.mjs` right after 202/203 went live, and
confirmed with a probe. A signed-in customer, with only the anon key and their
own session, could:

| Direct write | Was | What it voided |
|---|---|---|
| INSERT a requirement already `state='ready'` with any config | accepted, and dispatchable | 203's validation — incl. the dietary rule |
| UPDATE a requirement to `ready` | accepted | server-decided "missing" |
| Reset a dispatched requirement to `ready` | accepted | no-duplicate-dispatch |
| Rewrite `plan_code` | accepted | stable codes |

Own rows only (RLS held across tenants), and no money exposed — every line is
still priced by `resolve_booking`. Root cause: migration 190 line 227 grants
`authenticated` INSERT/UPDATE/DELETE on both plan tables, and 202/203's
server-owned columns inherited it.

**The fix** is a guard trigger per table that only applies when the caller is a
client role (`current_user` is `authenticated`/`anon`). It is `SECURITY
INVOKER` on purpose: inside 202/203's definer functions `current_user` is the
owner, so their writes pass. Column REVOKEs could not express the rules — an
upsert needs UPDATE on its own conflict keys, and `booking_line_id` is a
transition (null → your own line), not a permission.

**What still works, unchanged:** `savePlan`, `linkBookings`, `ensureEvent`,
`ensureRequirement`, `setFulfilmentMode` — every write the app makes today.

Three rules chosen so old APKs do not break:

- **A stale `decision` on a dispatched row is ignored, not refused.** `savePlan`
  re-sends `decision` for every row in one batched upsert; refusing would fail
  the whole save. It simply does not win.
- **Rebooking is allowed.** A requirement whose line expired or was cancelled
  may be linked to the customer's new booking. Never to null.
- **A dispatched requirement — or the event holding one — cannot be deleted.**
  A cascade runs as the table owner and would skip the requirement guard, so
  the event guard checks it too.

**Also adds the missing way back:** 202 moved a requirement to `dispatched` and
nothing ever moved it back. Now when its line **expires** it returns to `ready`
(the customer still wants it); when **cancelled**, to `selected` (sending it
again is a deliberate choice, not a side effect of the next tap).

## 205 — the dietary rule, corrected

203 was wrong three ways against the live catalogue: **vegan and jain dishes
were refused from veg menus** (`suggested_diet` has those values too); a
**mixed menu** (veg + non-veg ticked) got the veg restriction; and
`vegan_verified`/`jain_verified` were ignored. Now every dish must fit **at
least one** chosen diet, via one function — `sambramo_dish_fits_diets` — that
Menu Studio, substitutions and restaurant filters will share.
